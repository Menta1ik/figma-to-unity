# 🧠 Технические концепции: Figma Importer v2.5.4

Этот документ объясняет архитектурные принципы и ключевые механизмы, которые делают Figma Importer стабильным и производительным инструментом для Unity.

---

## 1. Система "Паспортов" (FigmaNodeId)

В основе системы "умной синхронизации" (Smart Sync) лежит концепция уникальных идентификаторов.

### Как это работает:
*   Каждый объект в Figma имеет уникальный `id` (например, `12:345`).
*   При импорте этот ID записывается в компонент `FigmaElement` на стороне Unity.
*   При **повторной синхронизации** плагин не просто создает новые объекты, а ищет в иерархии Unity объект с соответствующим ID.

### Почему это критично:
1.  **Сохранение компонентов**: Если вы добавили на кнопку свой скрипт `MyFancyAnimation.cs`, при обновлении верстки плагин найдет этот объект и обновит только его визуальные параметры (`Image`, `RectTransform`), сохранив ваш скрипт.
2.  **Ручное переименование**: В настройках (`FigmaImporterSettings`) можно включить опцию `Preserve Unity Names`. В этом случае, даже если вы переименовали "Button" в "Login_Submit_Btn" в Unity, плагин узнает объект по ID и не будет возвращать ему имя из Figma.

## 2. Service-Oriented Architecture (SOA)

Начиная с версии **2.3.1**, монолитный `FigmaParser` был разделен на независимые службы.

### Ключевые сервисы:
*   **ImageSyncService**: Изолирует сетевую логику. Использует `HttpClient` и семафоры (`SemaphoreSlim`) для управления параллельными загрузками. Это предотвращает "забивание" сетевого канала и ошибки 400 при импорте сотен иконок.
*   **PrefabManager**: Группирует логику работы с Asset Database. Гарантирует корректное сохранение префабов, создание папок и связку сцены с ассетами.

**Результат**: Код стал легче поддаваться модульному тестированию благодаря внедрению интерфейсов и DI-подобной структуры в обработчиках. Мы можем тестировать логику разбора нод без запуска полного цикла импорта. Это критично для поддержания стабильности в больших проектах.

## 3. Оптимизация кэширования (IconCandidateCache)

В Figma сложные векторные иконки часто состоят из десятков вложенных слоев (Paths, Vectors). 

### Проблема:
В ранних версиях `ImageHandler` рекурсивно обходил каждое дерево объектов, чтобы решить: "Это одна иконка, которую надо скачать как PNG, или это набор отдельных шейпов?". Это вызывало O(N²) нагрузку на больших макетах.

### Решение v2.3.1:
Введена система **IconCandidateCache**. Теперь результат анализа "является ли эта нода частью иконки" кэшируется на время жизненного цикла одного импорта. 
*   **Ускорение**: На макетах с >2000 объектами скорость обхода иерархии увеличилась в 3-5 раз.

## 4. Логика Layout и Alignment

Плагин автоматически переводит систему **Auto Layout** из Figma в компоненты Unity:
*   `Horizontal/Vertical Layout Group`
*   `Content Size Fitter`

### Особенности маппинга (v2.3.1):
Мы доработали логику выравнивания для крайних случаев. Например, комбинация `MAX/MAX` в Figma (Bottom-Right) теперь корректно транслируется в `TextAnchor.LowerRight` в Unity, что исправляет ошибки позиционирования текста, замеченные в версии 2.2.

## 5. Система Soft-Delete (Orphan tracking)

Что происходит, когда вы удалили кнопку в Figma и запустили синхронизацию?

### Режим Non-Destructive:
Плагин не удаляет объекты в Unity "втихую". Вместо этого:
1. Объект помечается как "сирота" (Orphan).
2. Ему добавляется компонент `FigmaOrphanedElement`.
3. В консоль выводится предупреждение.

Это защищает вас от случайной потери логики, которая могла быть привязана к удаленным элементам. Вы сами решаете, когда окончательно удалить объект из сцены.

## 6. Батчинг сетевых запросов

Figma API имеет лимиты на количество запросов и длину URL.
*   Плагин автоматически разбивает список иконок на пачки по **25 штук**.
*   Каждый батч обрабатывается отдельно.
*   Ошибки в одной иконке не прерывают загрузку остальных.

## 7. Adaptive Layout & Constraints Mapping (v2.5.4)

Для реализации адаптивности плагин преобразует систему **Constraints** из Figma в настройки **Anchors** и **Offsets** компонента `RectTransform`.

### Как работает маппинг:
1.  **LEFT / TOP**: Анкоры устанавливаются в `0` (или `1` для верха). Смещение (`offset`) фиксируется относительно родителя.
2.  **RIGHT / BOTTOM**: Анкоры устанавливаются в `1` (или `0` для низа). Расстояние рассчитывается от края родительского контейнера.
3.  **CENTER**: Анкоры устанавливаются в `0.5`. Объект позиционируется относительно центра родителя.
4.  **STRETCH (LEFT_RIGHT / TOP_BOTTOM)**: Анкоры растягиваются от `0` до `1`. Значения `RT.offsetMin/Max` сохраняют отступы (padding) от краев.
8.  **SCALE**: Анкоры устанавливаются в процентном соотношении от размера родителя (от `0` до `1`). В версии 2.5.4 мы уточнили расчеты, чтобы избежать накопления ошибок плавающей запятой при глубокой вложенности.
9.  **CENTER**: В версии 2.5.4 расчеты центрирования учитывают глобальное смещение родительского фрейма, что гарантирует идеальную соосность.

## 8. Stencil Guard & Hierarchy Flattening (v2.5.4)

В версии 2.5.4 мы решили критическую проблему Unity с переполнением буфера трафарета (Stencil Buffer).

### Механизмы защиты:
1.  **DismantleAllMaskContainers**: Перед каждым импортом плагин находит технические контейнеры `[Mask]` и «разбирает» их, возвращая объекты в общую иерархии. Это предотвращает бесконечное наслоение масок при повторных синхронизациях.
2.  **Глубина вложенности**: Плагин отслеживает уровень вложенности масок. Если глубина превышает **3**, следующая маска автоматически преобразуется в `RectMask2D`.
3.  **Auto-Fallback**: Простые прямоугольные маски или маски с высокой вложенностью автоматически заменяются на `RectMask2D`, что экономит Draw Calls и предотвращает ошибку `stencil mask depth > 8`.

## 9. Система логирования (FigmaLog) — v2.5.4

До v2.5.4 все хендлеры выводили `Debug.Log` на каждую ноду. При 500+ элементах консоль становилась бесполезной.

### Архитектура:
*   **FigmaLogLevel** (enum): `Silent`, `Minimal`, `Verbose` — определяется в `FigmaImporterSettings.logLevel`.
*   **FigmaLog** (static class, `Runtime/FigmaLog.cs`): Централизованный фасад с методами `Info()`, `Verbose()`, `Warning()`, `Error()`.
*   Уровень устанавливается автоматически при вызове `FigmaParser.RunSync()` / `ProcessFileAsync()`.

### Поведение по уровням:

| Уровень | Info | Verbose | Warning | Error |
| :--- | :--- | :--- | :--- | :--- |
| **Silent** | — | — | — | Всегда |
| **Minimal** | Да | — | Да | Всегда |
| **Verbose** | Да | Да | Да | Всегда |

*   `Error` выводится всегда, независимо от уровня — критические проблемы нельзя замалчивать.
*   `Verbose` — детали по каждой ноде (какой layout group назначен, какой шрифт заменён, какой тип маски выбран).
*   `Info` — итоги: количество загруженных картинок, результат сохранения префаба, обнаруженное разрешение.

## 10. Fill Container — layoutGrow (v2.5.4)

В Figma Auto Layout дочерний элемент с `layoutGrow = 1` означает «заполни всё свободное пространство по главной оси» (Fill Container).

### Как это работает в плагине:
1.  Поле `layoutGrow` уже десериализуется в `FigmaDataModels.cs` (было и до v2.5.4).
2.  `LayoutHandler.CanHandle()` теперь возвращает `true` для нод с `layoutGrow > 0`, даже если они сами не являются Auto Layout контейнерами.
3.  В методе `ApplyLayoutGrow()` плагин:
    *   Проверяет `context.ParentNode.layoutMode` — горизонтальный или вертикальный контейнер.
    *   Добавляет `LayoutElement` на объект.
    *   Устанавливает `flexibleWidth = layoutGrow` (для HORIZONTAL) или `flexibleHeight = layoutGrow` (для VERTICAL).

### Для дизайнеров:
Просто установите "Fill Container" на дочернем элементе Auto Layout фрейма в Figma. При синхронизации плагин автоматически применит `LayoutElement` с правильным значением `flexible`.
