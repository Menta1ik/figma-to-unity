# Figma → Unity: гайд для дизайнеров

Этот документ описывает **двойной набор требований** к макетам:

- **Стандартные требования** — хорошие практики подготовки UI-макетов в Figma.
- **Специфические требования плагина** — ограничения и правила, которые следуют из текущей реализации импорта в Unity.

Цель простая: чтобы макет не просто выглядел правильно в Figma, а **корректно переносился в Unity UI, был предсказуем в синке и не ломал иерархию, маски, текст и интерактивность**.

---

## Общие принципы

### Стандартные требования
- Один макет должен быть собран как понятная UI-структура, а не как набор декоративных слоёв.
- Каждый экран должен иметь читаемую иерархию: экран → секции → контейнеры → элементы.
- Повторяющиеся паттерны должны быть оформлены единообразно.
- Все ключевые элементы должны быть названы осмысленно.
- Дизайн должен быть технически воспроизводим, а не только визуально красив в Figma.

### Специфические требования плагина
- Плагин обходит Figma-дерево нодов рекурсивно и создаёт Unity-иерархию на основе структуры слоёв.
- Для каждого нода применяются отдельные обработчики: transform, layout, text, image, interactive.
- Поэтому структура Figma напрямую влияет на то, какие `RectTransform`, `LayoutGroup`, `Image`, `TextMeshPro` и UI-компоненты появятся в Unity.
- Если структура макета хаотична, плагин импортирует её так же хаотично.

## Экраны и верхнеуровневая структура

### Стандартные требования
- Каждый экран должен быть отдельным верхнеуровневым `Frame`.
- Один root frame = один экран, popup, panel или самостоятельный UI-блок.
- Не нужно складывать несколько независимых экранов в один общий контейнер.
- На верхнем уровне должны быть только крупные логические зоны: `Header`, `Body`, `Footer`, `Sidebar`, `Popup`.

### Специфические требования плагина
- Импорт строится от верхнего нода вниз, поэтому root frame становится фактической точкой входа для генерации Unity-иерархии.
- Имя импортируемого root frame используется как имя целевого импортируемого объекта и как основа для prefab naming.
- Если в одном root-контейнере смешано несколько экранов, результатом будет неудобная, перегруженная иерархия в Unity.

### Рекомендация
Хорошо:
- `Screen/MainMenu`
- `Screen/Shop`
- `Popup/ConfirmPurchase`

Плохо:
- один giant frame с несколькими экранами, модалками и hidden-вариантами внутри

## Контейнеры: Frame vs Group

### Стандартные требования
- Для всех значимых UI-контейнеров использовать `Frame`.
- `Group` допустим только как временная дизайнерская организация, но не как основа интерфейсной структуры.
- Всё, что ведёт себя как контейнер, должно быть контейнером и в Figma.

### Специфические требования плагина
- Плагин ожидает контейнерную логику через `Frame`, потому что именно там есть `Auto Layout`, `Clip content`, padding и resize behavior.
- `Group` не даёт полноценной layout-семантики и хуже маппится на Unity UI.
- Если экран собран на `Group`, Unity-иерархия получится визуально менее предсказуемой и сложнее для дальнейшей поддержки.

### Правило
- Контейнер с фоном, паддингами, вертикальным или горизонтальным составом — всегда `Frame`.
- `Group` не использовать для карточек, панелей, строк, хедеров, списков, viewport-областей.

## Auto Layout и layout-логика

### Стандартные требования
- Все списки, строки, карточки, тулбары, формы и повторяющиеся элементы должны собираться через `Auto Layout`.
- Нужно явно задавать направление (`Horizontal` / `Vertical`), spacing, padding и alignment.
- Resize behavior должен быть выбран осознанно: `Hug contents`, `Fill container`, `Fixed`.
- Не нужно компенсировать плохую структуру ручным позиционированием.

### Специфические требования плагина
- Плагин читает `layoutMode`, `itemSpacing`, `padding*`, `primaryAxisAlignItems`, `counterAxisAlignItems` и на этой основе строит Unity layout components.
- `Auto Layout` в Figma наиболее близок к `HorizontalLayoutGroup` / `VerticalLayoutGroup` в Unity.
- Если layout не описан, элемент импортируется как обычный `RectTransform` с абсолютным позиционированием.
- Это допустимо, но хуже переносится, хуже переживает изменения и хуже подходит для поддержки.

### Практические правила
- `Fixed` — для иконок, изображений, плашек, фонов, фиксированных кнопок.
- `Hug contents` — для текста, chip, label, кнопок, бейджей.
- `Fill container` — только для элементов, которые действительно должны растягиваться внутри родителя.
- Вложенные autolayout-контейнеры должны быть логичны и не избыточны.

## Позиционирование, размеры и геометрия

### Стандартные требования
- Использовать целые пиксельные значения там, где это возможно.
- Избегать случайных дробных размеров и координат.
- Не оставлять слои с нулевой шириной или высотой.
- Не создавать неоправданно сложные трансформации, повороты и вложенные offset-композиции.

### Специфические требования плагина
- Плагин читает `absoluteBoundingBox`, `absoluteTransform`, `rotation` и из них восстанавливает `RectTransform`.
- Нулевые размеры приводят к пустым или невидимым элементам в Unity.
- Дробные размеры и сложные вложенные смещения повышают риск визуальных артефактов после импорта.
- Повороты поддерживаются хуже, чем обычная ортогональная UI-геометрия, особенно во вложенных контейнерах.

### Правило
- UI должен быть собран как UI, а не как свободная плакатная композиция.
- Если элемент не обязан быть повёрнут — не поворачивать.

## Маски, clip и overflow

### Стандартные требования
- Для стандартной обрезки контента использовать `Frame + Clip content`.
- Маски использовать только тогда, когда действительно нужна нетривиальная форма.
- Избегать глубокой вложенности масок.
- Декоративные mask-конструкции без функциональной необходимости лучше не использовать.

### Специфические требования плагина
- `clipsContent: true` интерпретируется как прямоугольная обрезка и хорошо маппится на `RectMask2D`.
- `isMask: true` требует специальной логики: плагин создаёт служебный контейнер, переносит туда маску и связанные элементы.
- Для сложных фигур плагин может использовать stencil-based `Mask`, что тяжелее и чувствительнее к глубине вложенности.
- В реализации заложен защитный лимит по глубине stencil-масок, поэтому каскадные вложенные маски — плохой сценарий.

### Практическое правило
- Scroll area, card viewport, popup body, content clipping — только `Clip content`.
- Сложная фигурная маска — только если без неё действительно нельзя.
- Если визуальную задачу можно решить без маски, решать без маски.

## Текст и типографика

### Стандартные требования
- Использовать ограниченный, заранее согласованный набор шрифтов.
- Использовать ограниченный и осмысленный набор начертаний и размеров.
- Не смешивать стили внутри одного текстового блока без крайней необходимости.
- Названия текстовых слоёв должны отражать их роль: `Title`, `Subtitle`, `Price`, `Description`, `ButtonLabel`.

### Специфические требования плагина
- Плагин читает `characters`, `fontFamily`, `fontWeight`, `fontSize`, `lineHeightPx`, `letterSpacing`, text alignment и цвет.
- В Unity текст создаётся через TMP и зависит от `FontMappingTable`, где `font family + weight` должны быть сопоставлены с `TMP_FontAsset`.
- Если шрифт или вес не замаплен, результат в Unity будет неполным, некорректным или уйдёт во fallback.
- Mixed styles внутри одного текстового блока не являются надёжным сценарием для импорта как полноценной rich text-структуры.

### Правило
- Использовать только те шрифты и веса, которые подтверждены разработкой.
- Один текстовый слой = одна типографическая роль.
- Если нужен сложный смешанный текст, лучше обсудить это отдельно как исключение.

## Изображения, иконки и графика

### Стандартные требования
- Все графические элементы должны быть структурированы и названы так, чтобы было понятно, что это за asset.
- Иконки, изображения, background-элементы и декоративная графика должны быть отделены друг от друга логически.
- Нужно различать, что является контентным изображением, а что — просто фоновым shape.
- Избегать чрезмерно сложных, случайно собранных векторных конструкций.

### Специфические требования плагина
- Плагин обрабатывает image fill, solid fill и отдельные vector-like узлы по-разному.
- Векторные узлы и часть графики могут уходить в экспорт/скачивание как растровые изображения.
- Градиенты и сложные нестандартные заливки не являются надёжным стандартным сценарием для прямого импорта в uGUI.
- Поэтому всё критичное для визуального результата должно быть либо простым и предсказуемым, либо заранее подготовленным как asset.

### Правило
- Простая иконка = чистый векторный объект с понятным именем.
- Сложная декоративная графика = рассматривать как подготовленный asset.
- Градиентную или эффектную графику лучше не воспринимать как обычный runtime-UI primitive.

## Интерактивные элементы

### Стандартные требования
- Интерактивные элементы должны иметь явную структуру: контейнер, label, optional icon, state visuals.
- Кнопки, toggle, slider, input и scroll area должны быть собраны последовательно и одинаково внутри одной дизайн-системы.
- Название элемента должно отражать не только его визуальный вид, но и роль.

### Специфические требования плагина
- Плагин определяет часть интерактивных Unity-компонентов по ключевым словам в имени нода.
- Ключевые слова вроде `Button`, `Toggle`, `Slider`, `Scrollview`, `InputField` имеют функциональное значение.
- Внешний вид сам по себе не гарантирует, что элемент будет распознан как интерактивный Unity control.

### Правило
Использовать в названии контейнера понятные ключевые слова:
- `Button/Primary/Buy`
- `Toggle/Music`
- `Slider/Volume`
- `Scrollview/Rewards`
- `InputField/Email`

Если элемент по смыслу является кнопкой, но в имени этого не видно, разработка и импорт потеряют семантику.

## Иерархия и naming convention

### Стандартные требования
- Имена должны быть единообразными по всему проекту.
- Следует использовать понятную древовидную структуру имён.
- Не использовать мусорные автоматические названия вроде `Rectangle 17`, `Group 3`, `Text 91`.
- Не смешивать бессистемно языки, сокращения и нейминг-стили.

### Специфические требования плагина
- Имена нодов участвуют не только в читаемости, но и в функциональной интерпретации интерактивных элементов.
- Имя root node влияет на идентификацию импортируемого блока и naming результата.
- Хороший naming упрощает sync, отладку, навигацию по иерархии и последующую работу внутри Unity.

### Рекомендуемый шаблон
- `Screen/Shop`
- `Header/BackButton`
- `Header/Title`
- `Card/Product/Image`
- `Card/Product/Price`
- `Footer/BuyButton`

## Повторяющиеся элементы и компонентизация

### Стандартные требования
- Повторяющиеся элементы должны иметь одинаковую структуру.
- Все карточки одного типа должны быть собраны одинаково.
- Все строки списка, табы, item-плитки и form rows должны следовать одному шаблону.
- Варианты состояний должны быть системными, а не вручную собранными каждый раз заново.

### Специфические требования плагина
- Плагин лучше работает с предсказуемым повторяемым деревом, чем с визуально похожими, но структурно разными нодами.
- Если два элемента выглядят одинаково, но один собран через frame, другой через group, третий через случайный набор слоёв, после импорта это станeт заметной технической проблемой.

### Правило
Одинаковый UI-паттерн = одинаковая иерархия.

---

## Что особенно нежелательно

### Стандартные анти-паттерны
- хаотичная вложенность без логики
- контейнеры только ради визуального выравнивания
- смешение декоративных и функциональных слоёв без структуры
- избыточная глубина дерева
- несистемный naming
- произвольные размеры и отступы

### Анти-паттерны для текущей реализации плагина
- `Group` вместо `Frame` для UI-контейнеров
- сложные каскадные mask-сценарии
- mixed styles в одном текстовом блоке
- неутверждённые шрифты и веса
- интерактивные элементы без ключевых слов в имени
- градиенты как критичная часть стандартного UI
- сложные повёрнутые вложенные структуры

---

## Минимальный чеклист перед передачей макета

- Каждый экран — отдельный root `Frame`
- Важные контейнеры собраны на `Frame`, а не на `Group`
- Для повторяющихся структур используется `Auto Layout`
- Padding, gap, alignment и resize behavior заданы явно
- Для прямоугольной обрезки используется `Clip content`
- Маски используются только там, где без них нельзя
- Все тексты используют согласованные шрифты и веса
- Интерактивные элементы содержат ключевые слова в имени
- Все слои и контейнеры названы осмысленно
- Структура повторяющихся элементов единообразна
- Нет нулевых размеров, мусорных названий и лишней вложенности

---

## Короткая формула

Хороший макет для этого плагина — это макет, который:

1. логично собран как UI,
2. системно назван,
3. использует `Frame`, `Auto Layout` и `Clip content` там, где это ожидается,
4. не злоупотребляет mask-логикой,
5. использует только согласованную типографику,
6. явно обозначает интерактивные элементы,
7. даёт плагину понятную, стабильную структуру для импорта в Unity.
